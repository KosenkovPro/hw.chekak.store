# План разработки кроссплатформенного диспетчера задач на Rust

**Название проекта:** MCPad. Cargo workspace — `mcpad`, единое ядро — `mcpad-core`.
**Расположение кода:** `hw.chekak.store/mcpad/` — workspace внутри папки проекта; документация (README, сравнение, этот план) остаётся в корне `hw.chekak.store/`.
**Язык/стек:** Rust 2024 edition, MSRV 1.99, cargo workspace, egui/eframe (десктоп) + ratatui (терминальный TUI).
**Целевые платформы:** Windows 10 1809+/11 x64 (и ARM64), Ubuntu 22.04+/24.04+ x64 (и ARM64), macOS 13+ (Apple Silicon и Intel).
**Лицензия:** MIT или Apache-2.0 (двойная лицензия, как у всех MIT-проектов в сравнении).

Документ опирается на разбор четырёх проектов из [README.md](README.md) и [comparison.html](comparison.html) и на код RustWTM, лежащий в `../RustWTM` (MIT, ~107 000 строк Rust в 8 крейтах). Файлы README.md и comparison.html этим планом не изменяются.

> **Решения зафиксированы 18.11.2026** — см. [§9](#9-зафиксированные-решения-и-оставшиеся-вопросы): новая workspace с выборочным портом RustWTM; egui/eframe + ratatui; без kernel-драйвера в v1.0; удалённый мониторинг минимально с mTLS; плагины — WASM (wasmtime); бесконечный canvas в двух режимах + миникарта; JSON-темы применяются в рантайме напрямую в `egui::Visuals` и в стили `ratatui`.

**Ключевой вывод сравнения:** функционального «всего сразу» в одном приложении на трёх ОС без потерь не существует — либо пропадает глубина инспекции, либо честность метрик. Поэтому план строится не на «всё или ничего», а на **трёхуровневой честности**:

- **Tier A — паритет:** есть на всех трёх ОС одинаково.
- **Tier B — best effort:** реализовано там, где ОС даёт API; на остальных — понятная заглушка с причиной.
- **Tier C — платформенно:** только на одной ОС (например, управление вентиляторами только в Linux).

Каждое измерение несёт **provenance** (источник, уверенность, возраст данных) и никогда не подменяет неизвестное нулём — прямое заимствование из gputaskman и лучшее решение из всего сравнения.

## 1. Продуктовая цель и границы

**Что это:** единый кроссплатформенный диспетчер процессов и монитор железа, который одновременно (а) показывает, что происходит, (б) объясняет, почему это происходит, (в) может вмешаться по заранее заданным правилам.

**Ключевые свойства продукта:**

1. **Честные метрики.** Каждое число помечено источником и уровнем уверенности: `Measured` (измерено), `Inferred` (выведено), `Estimated` (оценено), `Unavailable` (нет данных с причиной). Никогда не подставляем 0 вместо неизвестного.
2. **Безопасные действия.** Управление процессом — по воле пользователя или по правилу, но всегда с журналом, откатом и режимом dry-run по умолчанию. Никаких необратимых действий без явного подтверждения.
3. **Минимальные привилегии.** Приложение работает от обычного пользователя. Повышенные возможности — по требованию, через отдельный помощник или сервис, а не «система по умолчанию».
4. **Локальность.** Никакого обязательного облака. Удалённый мониторинг и AI — опциональные и локально исполняемые там, где это возможно.
5. **Расширяемость.** Плагины — изолированный WASM, а не нативный код.

**Явно не входит в объём v1.0:**

- Нативный kernel-драйвер с перехватом создания процессов (Windows) — откладываем, см. фазу M11 как опцию.
- Собственный веб-сервис/аккаунты/телеметрия вендора.
- Чтение памяти чужих процессов на macOS (система не даёт без root) и на Linux (нужен `CAP_SYS_PTRACE`).
- Перехват трафика, DPI, файрвол уровня приложения — вне диспетчера.
- Копирование кода Task Explorer (GPL).

   │  ├─ mcpad-backends/

**Правило по `unsafe`:** весь `unsafe` изолирован в `mcpad-backends/*` и `mcpad-inspect` (там, где нужен FFI к libdwfl/Metal/DBus). Крейты `mcpad-core`, `mcpad-policy`, `mcpad-history`, `mcpad-ipc`, `mcpad-cli`, `mcpad-mcp` — `unsafe`-free и `#![forbid(unsafe_code)]`. Это прямое наследование подхода RustWTM (`wtm-sys` — единственный крейт с unsafe).

**Профиль `mcpad-core`:** ядро — единственный источник правды о модели данных, поэтому он остаётся лёгким: `serde` + `alloc`, без GUI, без `tokio`, без платформенных зависимостей. Это даёт свободное встраивание в консольный режим, MCP и будущие клиенты (встраиваемые цели — не цель v1.0, но ограничение «ядро не тяжелеет необходимого» сохраняется).

**Границы процессов:**

- `mcpad-sampler` — единственный владелец системных запросов; GUI, CLI, MCP и удалённый клиент читают один и тот же кэш снимков. Это убирает дублирование и «разные числа в разных окнах».
- `mcpad-policy` — чистые функции: на входе снимок + правила → на выходе план действий. Никаких системных вызовов. Это делает политику полностью тестируемой на фикстурах.
- `mcpad-action` — единственное место, где что-то меняется в системе. Каждое действие проходит через проверку прав, политику dry-run и аудит.

### 2.2 Модель данных (ядро всего)

```rust
pub struct Counter<T> {
    pub value: Option<T>,            // None = неизвестно, НЕ ноль
    pub source: Source,              // WddmPdh, Nvml, DrmFdinfo, Metal, Procfs, Cgroup, ...
    pub confidence: Confidence,      // Measured | Inferred | Estimated
    pub age: Option<Duration>,       // возраст данных
    pub unavailable_reason: Option<UnavailableReason>,
}

pub enum Confidence { Measured, Inferred, Estimated }
```

Один и тот же тип используется для VRAM, температуры, CPU%, числа хэндлов и скорости сети. Это делает «нет данных» первоклассным значением во всём приложении и в экспорте.

**Идентичность процесса:** `ProcessKey { pid: u32, start_time: SystemTime, boot_id: Uuid }` — переживает переиспользование PID и перезагрузку (необходимо для `diff`/`record`).

**Снимок:** `Snapshot { schema_version, taken_at, system: SystemInfo, processes: Vec<ProcessInfo>, gpus: Vec<GpuDevice>, sensors: Vec<Sensor>, services: Vec<ServiceInfo>, events: Vec<Event> }` — сериализуется в JSON по фиксированной схеме (совместимая с форматом gputaskman по полям GPU, чтобы `diff` работал с обоими).

### 2.3 Ядро платформенных бэкендов

| Задача | Windows | Linux | macOS |
|---|---|---|---|
| Список процессов | `NtQuerySystemInformation(SystemProcessInformation)` | `/proc/<pid>/stat`, `status` | `libproc::proc_listpids` + `proc_pidinfo` |
| CPU% процесса | Δ kernel+user / Δ wall / лог. ядра | `/proc/<pid>/stat` utime+stime | `proc_pid_rusage` (`task_info`) |
| Родитель / дерево | `ProcessBasicInformation` | `/proc/<pid>/stat` ppid | `proc_bsdinfo` ppid |
| Память | `GetProcessMemoryInfo` + commit | `/proc/<pid>/status` (RSS, private), `smaps_rollup` | `proc_pid_rusage` + `footprint` (частично, только свои) |
| Потоки | `NtQuerySystemInformation(Thread)` | `/proc/<pid>/task` | `proc_taskinfo` |
| Стеки потоков | `StackWalk64` + DbgHelp, символы MS | `libdwfl` (elfutils) или `gimli`/`addr2line` по `/proc/<pid>/maps` | `proc_pidinfo` (только свои) |
| Хэндлы | `NtQuerySystemInformation(SystemHandleInformation)` | `/proc/<pid>/fd` + `fdinfo` | `proc_pidfdinfo` (только свои) |
| Модули | `EnumProcessModules` + `LdrQueryDll` | `/proc/<pid>/maps` (исполняемые регионы) | `proc_pidinfo` images |
| Сокеты | `GetExtendedTcpTable`/`UdpTable` | `sock_diag` netlink | `proc_pidfdinfo` + `netstat`-совместимый слой |
| Службы | SCM (`OpenSCManager`) | systemd через D-Bus | `launchd` через `launchctl` |
| Файловые дескрипторы → владелец | `NtQuerySystemInformation` + `FileProcessLink` | `/proc/*/fd` скан | ограниченно |
| События процесса | ETW Kernel-Process | proc connector / eBPF | kqueue/process events частично |
| Трафик по процессам | ETW Kernel-Network | eBPF (нужен root) / nethogs-подход | `libproc` socket buffers + `nettop`-подобный доступ (ограниченно) |
| Активность файлов по процессам | ETW FileIo | eBPF/audit | ограниченно |
| Сенсоры | WMI (MSAcpi_ThermalZoneTemperature, Win32_Perf*) | `hwmon`, `sysfs/class/thermal` | `IOReport`/`IOKit` (SMC — Apple Silicon) |
| Температура CPU | WMI/Win32_Perf, `MSAcpi` | `hwmon` (`coretemp`, `k10temp`) | `IOReport` (Apple Silicon) |
| Частоты, питание | PDH, WMI | `hwmon`, `cpufreq` | `IOKit` (`IOReport`) |
| GPU | PDH «GPU Engine» + NVML + ADL/AMD SMI | NVML + DRM fdinfo (amdgpu/i915/xe) + amdsmi | Metal (`MTLCopyAllDevices`) + `footprint` |
| Блок-лист/запрет запуска | IFEO `Debugger` / ETW / AppLocker | без общего механизма (Tier C): cgroups+systemd+LSM | нет (Tier C) |
| Лимит CPU | Job Object `JOB_OBJECT_CPU_RATE_CONTROL_HARD_CAP` | cgroup v2 `cpu.max` | нет (Tier C): только nice/QoS |
| Лимит памяти | Job Object `JOB_OBJECT_JOB_MEMORY_LIMIT` | cgroup v2 `memory.max` | нет (Tier C) |
| Приоритет | `SetPriorityClass` | `setpriority` | `setpriority` |
| Affinity | `SetProcessAffinityMask` / CPU Sets | `sched_setaffinity` | нет на уровне процесса (Tier C) |
| Suspend/resume | `NtSuspendProcess` / `NtResumeProcess` | `SIGSTOP` / `SIGCONT` | `SIGSTOP` / `SIGCONT` |
| Завершить дерево | Toolhelp32 | process group + cgroup `cgroup.kill` | process group |
| Освободить RAM | `SetProcessWorkingSetSizeEx` | cgroup `memory.reclaim` | нет: только сигналы memory pressure |
| Захват дампа | MiniDumpWriteDump | `gcore`/ptrace | `sample`/`lldb` (только свои) |

### 2.4 Параллельность и производительность

- Сэмплер — `tokio`-task с приоритетами: быстрый путь (процессы, CPU, RAM) раз в 1 с, медленный (GPU, сенсоры, диск SMART, Docker) — по расписанию с джиттером.
- Тяжёлые запросы (SMART, `smaps`, stack unwinding, WMI) — только по явному запросу пользователя или в фоне с низким приоритетом, никогда не в горячем пути кадров UI.
- Кольцевые буферы в памяти — графики; SQLite — долгосрочная история (по умолчанию 30 дней, сжатие до 1 минуты при повышении объёма).
- Бюджеты: список 1000 процессов ≤ 50 мс; UI 60 fps при 5000 процессов; холодный старт ≤ 1.5 с; RSS приложения ≤ 150 МБ.

### 2.5 Темы, бесконечный canvas и терминальный режим

**Темы (JSON, применяются в рантайме).** UI нативный на egui, без WebView, поэтому тема — это JSON, который разбирается и валидируется один раз, а затем применяется напрямую в `egui::Visuals` и в палитру canvas-рендера; терминальный режим получает из той же темы стили `ratatui`. Горячая перезагрузка темы без перезапуска приложения; тема задаёт палитру, типографику, радиусы, плотность строк, акценты статусов (ok/предупреждение/критично) и цвета графиков. Один источник правды для трёх представлений (десктоп, canvas, терминал).

**Бесконечный canvas (`mcpad-canvas`).** Новая функция, которой нет ни в одном из четырёх проектов-аналогов: интерактивный граф на egui Painter с бесконечным холстом.

- **Два режима:** (1) дерево процессов как граф — узлы-процессы, ортогональные стрелки, группировка по пользователю и по приложению; (2) граф зависимостей модулей — кто что загрузил, с размерами и подписями.
- **Миникарта** с текущим viewport, перетаскиванием и рамкой выделения.
- **Производительность:** 60+ FPS на больших графах (целевой ориентир — 10 000 узлов) за счёт пространственного индекса (quadtree/сетка), отсечения невидимых узлов, уровней детализации (LOD) и батчинга команд Painter.
- **Интерактив:** zoom/pan, выделение узла с подсветкой ветки, поиск по узлам, «развернуть поддерево», экспорт графа в PNG/SVG и в JSON.
- **Перенос из RustWTM:** рендер ropey-буфера (длинные логи и дампы памяти без копий), вкладки, подсветка синтаксиса — берём проверенные решения и переносим в чистый workspace.

**Терминальный режим (`mcpad-tui`).** ratatui поверх того же ядра: список процессов, GPU-панель и дерево в терминале, вывод `--once`/`--json`, тот же формат снимка, что и у десктопа. Режимы совпадают по данным, различаются только представлением.

## 5. Модель безопасности и привилегий

Три уровня исполнения, переключаемые явно:

1. **Пользовательский (по умолчанию).** Только чтение + действия над собственными процессами. Никаких служб при первом запуске.
2. **Повышенный помощник.** Запускается по требованию для конкретных задач (чтение чужих процессов, `memory.reclaim`, fan control, eBPF). Живёт недолго или по явному разрешению.
3. **Фоновый сервис.** Governor, правила, блокировки, мониторинг 24/7. Настраивается отдельно и **никогда не создаётся при установке без согласия**.

**Отличия от RustWTM (осознанные):** служба не стартует как SYSTEM по умолчанию; используется least-privilege (на Linux — отдельный пользователь без shell, на macOS — launchd агент, на Windows — сервис с минимальными правами и UAC). Dry-run — режим по умолчанию для любых автоматических действий.

**Дополнительно:**

- Все автоматические решения журналируются: что, почему, по какому правилу, с какими значениями снимка.
- Команды, изменяющие систему, требуют подтверждения в GUI и в CLI (например, `--yes`).
- Секреты (API-ключи AI) — DPAPI (Windows), Keychain (macOS), Secret Service (Linux).
- Плагины — WASM в песочнице: без файловой системы, сети и произвольных вызовов по умолчанию; доступ выдаётся по запросу.
- Обновления — с проверкой подписи издателя и SHA-256; отказ от неверного издателя.

## 8. Тестирование и валидация

**Уровни:**

- **Юнит-тесты:** чистая логика (`mcpad-policy`, `mcpad-core`, `mcpad-history`, расчёт дельт).
- **Фикстурные тесты счётчиков:** записанные JSON-ответы WDDM/PDH, DRM fdinfo, NVML, Metal → проверка парсинга и семантики без железа. Именно так проверяется корректность «null ≠ 0».
- **Интеграционные на CI:** полный снимок против эталонного (golden) JSON, с послаблениями на время/ordering.
- **Стенд железа:** 8–10 машин — Win11 (Intel+AMD+NVIDIA), Win11 ARM64, Ubuntu 24.04 (NVIDIA/AMD/Intel), Ubuntu 22.04, macOS 14/15/26 (Apple Silicon), macOS Intel. Для каждой — эталонные значения (`nvidia-smi`, `intel_gpu_top`, `nvidia-smi pmon`, `sensors`).
- **Визуальный CI:** рендер ключевых экранов в 4 DPI, 2 темы, 3 языка.
- **Тесты безопасности:** dry-run не меняет систему; непривилегированный режим не может выполнить привилегированное действие; плагин не выходит за песочницу; аудит содержит каждое действие.
- **Нагрузочные:** 5000 процессов, 10 минут сбора, проверка роста RSS и задержек.

**Определение «готово» для фазы:** функция работает на всех трёх ОС (или честно недоступна с причиной), покрыта тестами, документирована в `docs/`, не ломает линты, проходит ревью.

1. **Raw-строки темы были сломаны.** В `mcpad-theme` тема с цветами вида `"#rrggbb"` была записана как `r#"…"#`; в Rust такая строка обрывается на первом `"#`, то есть файл не компилировался. Исправлено на `r##"…"##`.

Руслан toolchain установлен в `D:\app\Rust`: cargo/rustc 1.100.0, clippy 0.1.100, rustfmt 1.11.0, MSVC Build Tools 18. Workspace собирается, тесты зелёные, clippy и rustfmt чистые — то есть пункты «не проверено» из волн 1 и 2 про сборку закрыты.

**Цепочка CI на живой машине:**

| Шаг | Команда | Результат |
|---|---|---|
| Сборка | `cargo build --workspace` | успех |
| Тесты | `cargo test --workspace --no-fail-fast` | 134 теста в 23 наборах, 0 падений |
| Clippy | `cargo clippy --workspace --all-targets --all-features -- -D warnings` | 0 замечаний |
| Формат | `cargo fmt --all -- --check` | 0 расхождений |

**MSRV исправлен:** в манифесте стояло 1.85, а `egui`/`eframe` 0.37 требуют ≥ 1.95 — сборка на заявленном MSRV была невозможна в принципе. Поставлено 1.99 (как в §9, D1), `Cargo.lock` пересобран под него.

**Что нашлось при первой настоящей сборке (исправлено):**

*Ошибки компиляции.* Набор features `windows 0.62` и раскладка функций по модулям привязок (`OpenProcessToken` — в `Threading`, `GetComputerNameW` — в `WindowsProgramming`, `GlobalMemoryStatusEx` — в `SystemInformation`); в egui/eframe 0.37 — `eframe::App::logic`/`ui` вместо `update`, `egui::Panel::top`/`right` вместо `TopBottomPanel`, `allocate_exact_size`, `StrokeKind::Middle`, `from_rgba_unmultiplied`, `all_styles_mut`/`style_of`, `TextStyle` больше не `Copy`.

*Clippy и формат.* 24 замечания `undocumented_unsafe_blocks` (unsafe-блоки без SAFETY-комментариев — их теперь 41, и все задокументированы, включая linux- и macOS-бэкенды, которые собираются только в CI); новые линты Rust 1.100 — `is_multiple_of` и `collapsible_if`; `cargo fmt` привёл 38 файлов к единому виду.

*Дефекты в данных — их нашла сверка с системой, а не компилятор.*

1. **Раскладка `SYSTEM_PROCESS_INFORMATION` была сдвинута на 0x28.** Хвост структуры читался не с тех мест: `PagefileUsage`, `PeakPagefileUsage`, `PrivatePageCount` и 64-битные счётчики ввода-вывода. Сверено с `GetProcessMemoryInfo` и `GetProcessIoCounters` на живой машине, тест смещений переписан по `phnt.h`.
2. **Время CPU не измерялось ни у одного процесса.** `UserTime`/`KernelTime` — это длительности, а не отметки времени, а из них вычиталась эпоха Windows, поэтому результат всегда был отрицательным. Теперь это `windows_duration_to_nanos`.
3. **Приватная память не совпадала с `Get-Process` ни у одного процесса** — бралось не то поле. Теперь берётся `PrivatePageCount` (0xC8), значение совпадает с `PrivateMemorySize64`.
4. **Признак защищённого процесса читался из поля, которого в структуре нет** — значение всегда было нулём, то есть «не защищён» вместо «неизвестно». Поле `is_protected` стало `Option<bool>` и на Windows остаётся `None`: признак требует отдельного запроса к каждому процессу, а не честного нуля.
5. **`mcpad info` падал с access violation.** Буфер `u8` кастовался к структуре с указателем — это UB. Перешли на `read_unaligned` и чтение UTF-16 из своего буфера.
6. **`LookupAccountSidW` с `NULL` в последнем параметре тоже роняет процесс.** Документация называет параметр необязательным, но API пишет в него — передаём настоящий указатель.
7. **Длинная командная строка не помещалась в буфер 4 КБ** и молча превращалась в «—». Теперь размер уточняется у ядра и запрос повторяется.
8. **Лишнее право `PROCESS_VM_READ`** в `OpenProcess` закрывало доступ к процессам, доступным только для чтения.
9. **PID 0 оставался без имени** («pid-0») — теперь «System Idle Process».
10. **В CLI доля CPU всегда была «—»**: один замер не даёт дельты. Добавлен второй замер с интервалом (`--interval-ms`, по умолчанию 300 мс); `mcpad once` остаётся одиночным снимком.
11. **`os_version` дублировал имя ОС** («Windows Windows 10.0.26100») — теперь «Windows 10.0.26100».
12. **Бинарь назывался `mcpad-cli.exe`** — переименован в `mcpad.exe`, как в документации.

Эталон — `Get-Process`, `Win32_Process` (WMI) и напрямую `GetProcessMemoryInfo`/`GetProcessIoCounters`. До правок время CPU и приватная память не совпадали ни у одного процесса.

**Проверено вживую:** `mcpad list` (текст и JSON) с измеренной долей CPU; `mcpad info` — путь к образу, командная строка и владелец сходятся с системными; `mcpad capabilities`; `mcpad once`; окно GUI открывается и работает без падения (содержимое вручную не проверялось).

**Release-сборка и замер времени снимка.** Критерий из M1 (§7): «список 1000 процессов ≤ 50 мс».

* `cargo build --workspace --release` — 3 мин 22 с (LTO fat, `codegen-units = 1`); `mcpad.exe` — 0,8 МБ, `mcpad-gui.exe` — 12,7 МБ.
* Замер сделан отдельной командой `mcpad bench [--samples N] [--json]`: она меряет полный сбор данных (обращение к ОС плюс разбор), первый вызов уходит на прогрев.

| Процессов | минимум | медиана | среднее | максимум |
|---|---|---|---|---|
| 296 (обычная нагрузка) | 3,44 мс | 3,78 мс | 3,77 мс | 4,23 мс |
| 1097 (под нагрузкой) | 7,52 мс | 11,09 мс | 11,07 мс | 14,94 мс |

Нагрузка настоящая, а не экстраполяция: поднято около 800 лёгких `ping` до общего числа 1097 процессов, замер снят, нагрузка убрана — машина вернулась к 295 процессам, следов не осталось.

**Критерий выполнен с запасом:** на 1097 процессах медиана 11,09 мс — в 4,5 раза быстрее требуемых 50 мс. По двум точкам (296 и 1097 процессов) постоянная часть снимка — около 1,1 мс, а стоимость одного процесса — около 9,1 мкс, то есть на ровно 1000 процессах ожидается ≈ 10,2 мс. Разброс (7,5–14,9 мс) объясняется тем, что машина была занята: WSL и QEMU забирают заметную часть CPU.

### Волна 4 — кроссплатформенная сборка, перечисление модулей, MSRV

Главная находка волны: **сборка всего workspace на Linux и macOS была сломана**, и CI-матрица падала бы на двух ОС из трёх. Причина в том, что волны 1–2 проверялись только на Windows: модули `sys` в linux- и macOS-бэкендах помечены `#[cfg(target_os = "...")]`, поэтому никогда не компилировались, а крейт `windows` целиком `#![cfg(windows)]` — и его зависимость `windows-future` не собирается вне Windows.

Проверка сделана через `cargo check --target`: поставлены цели `x86_64-unknown-linux-gnu` и `aarch64-apple-darwin`, workspace проверяется целиком, вместе с тестами (`--all-targets`).

**Что было сломано (исправлено):**

1. **windows-бэкенд не собирался вне Windows.** Привязка `windows` перенесена в `[target.'cfg(windows)'.dependencies]`, сам крейт помечен `#![cfg(windows)]`: вне Windows он собирается пустым, но остаётся членом workspace.
2. **linux-бэкенд никогда не компилировался.** В `module_links` вызывался `.filter()` у `Result`, а не у `Option`. Теперь `.ok().map(…).filter(…)`.
3. **macos-бэкенд не собирался на macOS.** У `libc::sysctl` на Apple первый параметр — `*mut c_int`, а код передавал `*const c_int`. Массив `mib` сделан изменяемым.

После правок `cargo check --workspace --all-targets` зелёный на `x86_64-unknown-linux-gnu` и `aarch64-apple-darwin`.

**MSRV подтверждён на деле.** Заявленные 1.99 (в плане D1 — 1.99.1) проверены установленным тулчейном: `cargo +1.99 check --workspace --all-targets --locked` проходит. Раньше цифра стояла только в манифесте.

**Перечисление модулей на Windows.** `Capability::ProcessModules` перестал быть «unsupported»: список модулей берётся из `EnumProcessModules`, путь к каждому — из `GetModuleFileNameExW` (psapi). Добавлена команда `mcpad modules <pid>`. У `explorer` — 279 модулей с путями, у `pwsh` — 119; путь, который узнать не удалось, остаётся `None` («неизвестно»), а не пустым. У защищённого процесса — честная ошибка доступа, а не пустой список. Тесты: модули текущего процесса перечисляются и содержат `kernel32`; несуществующий процесс даёт ошибку.

**CI-воркфлоу дополнен.** Задача `build` осталась прежней (сборка, clippy, fmt, тесты на трёх ОС в профилях dev и release), добавлены:

* `msrv` — сборка на Rust 1.99, чтобы новое в коде ломало сборку сразу, а не на волне спустя;
* `smoke` — CLI собирается в release и запускается на всех трёх ОС: `list --json`, `capabilities`, `bench`, `modules` (перечисление модулей проверяется только там, где платформа его поддерживает).

**Осталось не проверенным:** сами тесты на Linux и macOS (сборка и проверка компиляции — да, запуск — нет: нужны эти машины или CI), производительность canvas на 10 000 узлов, перечисление модулей на macOS (из чужого процесса список модулей штатно не достаётся — платформа честно отвечает «не реализовано»), поведение GUI под нагрузкой. Критерий «1000 процессов ≤ 50 мс» проверен на Windows; на Linux и macOS его ещё нужно подтвердить.

**Следующий шаг:** прогнать CI на реальных Ubuntu и macOS (первый настоящий запуск матрицы), снять ту же метрику времени снимка на этих ОС, перечисление модулей на macOS.

### Волна 5 — релиз v0.1.0 на GitHub

Волна закрывает два незакрытых пункта волны 4: CI наконец прогнан на настоящих Ubuntu и macOS, и собраны готовые бинари под пять платформ.

**Главная находка волны: воркфлоу лежали не там, где их читает GitHub.** Файлы `.github/workflows/` были положены в `mcpad/.github/workflows/`, а Actions читает только корневой `.github/workflows/`. Ни один прогон никогда не запускался бы сам — команды `git push` проходили, а проверки не выполнялись. Воркфлоу перенесены в корень репозитория, `working-directory: mcpad` задан в них самих.

**Что чинилось по ходу (три итерации прогона):**

1. **Пути к артефактам.** `actions/upload-artifact` считает пути от корня репозитория, а сборка идёт в `mcpad/`. Пути исправлены на `mcpad/dist/…`, скачивание — в `$GITHUB_WORKSPACE/artifacts`.
2. **Линты на macOS.** `let mut size` там не нужен — убрано. Крейт `windows` объявлен неиспользуемой зависимостью вне своей ОС — зависимость перенесена в целевую секцию.
3. **Дымовой шаг на Windows.** Git Bash на Windows транслирует `$$` в пустую строку, и PID процесса подставлялся как пустой. На Windows используется PowerShell `$PID`, на Unix — `$$`.

**Сборка релиза.** Пять платформ на нативных раннерах GitHub — кросс-компиляция с Windows на macOS/Linux нереалистична, а нативные раннеры дают все пять сразу. Архивы: zip для Windows, tar.gz для Unix; в каждый — `mcpad` (CLI), `mcpad-gui` (окно) и папка `themes/`. Рядом — файл `.sha256`.

| Платформа | Архив | Размер |
|---|---|---|
| Windows x64 | `mcpad-v0.1.0-x86_64-pc-windows-msvc.zip` | 6,05 МБ |
| Linux x64 | `mcpad-v0.1.0-x86_64-unknown-linux-gnu.tar.gz` | 7,99 МБ |
| Linux ARM64 | `mcpad-v0.1.0-aarch64-unknown-linux-gnu.tar.gz` | 7,36 МБ |
| macOS ARM64 | `mcpad-v0.1.0-aarch64-apple-darwin.tar.gz` | 4,68 МБ |
| macOS x64 | `mcpad-v0.1.0-x86_64-apple-darwin.tar.gz` | 5,15 МБ |

**CI прогнан вживую, все 10 задач зелёные:** `windows-latest` / `ubuntu-latest` / `macos-latest` в профилях dev и release (форматирование, clippy с `-D warnings`, тесты, сборка), MSRV 1.99 и три живых смоук-прогона CLI — `list --json`, `capabilities`, `bench`, `modules`. **Тесты на Linux и macOS выполнены впервые** — до этого эти ОС проверялись только компиляцией.

**Релиз проверен по факту, а не по факту публикации.** Все пять архивов скачаны, у каждого сверен SHA-256 с опубликованной контрольной суммой — совпало везде. Формат и архитектура бинарей подтверждены по сигнатуре: Linux — ELF x86-64 и AArch64, macOS — Mach-O x86_64 и arm64. Windows-сборка запущена прямо из распакованного архива: `list` (302 процесса), `capabilities`, `bench` (медиана 3,86 мс на 303 процесса), `info` (путь, командная строка, владелец — верно), `modules` (142 модуля pwsh с путями); окно GUI открылось с заголовком «MCPad» и завершилось без ошибок в stderr.

**Осталось не проверенным:** критерий «1000 процессов ≤ 50 мс» на Linux и macOS (замер сделан на Windows), производительность canvas на 10 000 узлов, перечисление модулей на macOS (платформа честно отвечает «не реализовано»), поведение GUI под нагрузкой, macOS-сборки не подписаны — первый запуск потребует подтверждения в Gatekeeper.

**Следующий шаг:** снять метрику времени снимка на Linux и macOS, разобрать пути модулей macOS, подписать сборки macOS.

### Волна 6 — новая оболочка графического интерфейса

Запрос был прямой: «интерфейс крайне плохой… возьми один из интерфейсов программ исходных, сделай подобный, просто вот расширив функционал. Посмотри, какой интерфейс в интернете хвалят больше всего, и используй его».

**Выбор сделан по проверяемому признаку, а не по вкусу.** Поиск по отзывам о диспетчерах процессов сходится на двух именах: Диспетчер задач Windows 11 (2025) и System Informer. Первый хвалят за сайдбар с навигацией, командную панель, тепловую карту в колонках, живые крупные графики, сортировку по заголовкам и выбор столбцов; второй — за тёмную тему, дерево, настраиваемые колонки и подсветку строк. Взят первый как каркас, второй — как источник приёмов; код Task Explorer (GPL-3.0) не копировался, всё написано с нуля.

**Каркас окна.** Слева — сворачиваемый сайдбар со значками, нарисованными линиями (не символами шрифта: одинаково на любой системе), сверху — командная панель с поиском, заморозкой, переключением темы и языка, снизу — строка состояния (время снимка, число процессов, интервал), справа — сворачиваемая панель сведений.

**Функционал расширен сверх Диспетчера задач:**

| Приём | Что даёт |
|---|---|
| Тепловая карта в колонках CPU и памяти | нагрузка видна без чтения чисел; неизвестное значение **не красится** — «нет данных» и «ноль» не путаются |
| Спарклайны CPU в таблице | видно не только «сейчас», но и динамику процесса |
| Сортировка по заголовкам | переключение направления; отсутствующие значения **всегда в конце** при любом направлении |
| Выбор столбцов (10 штук) | плотность по вкусу: PID, имя, CPU, память, приватная память, потоки, дескрипторы, чтение/запись I/O, история |
| Плотность строк | «обычно» и «компактно» |
| Панель сведений | ресурсы, сведения о процессе и **происхождение данных**: источник и уверенность каждого счётчика |
| Запрос подробностей по требованию | путь, командная строка и владелец запрашиваются при выборе процесса, а не тянутся в горячий путь |
| Горячие клавиши | F6 — заморозка, Ctrl+F — поиск, Ctrl+1…5 — переключение разделов, Esc — очистить |
| `--view` | открытие сразу на нужном разделе: `processes`, `tree`, `performance`, `canvas`, `capabilities` |

**Разделы приведены к одному языку.** «Дерево» переписано на ручную отрисовку с колонками «Имя / CPU % / Память, МБ» (раньше значения прижимались к правому краю каждой строки отдельно), «Возможности» — из плоского списка в карточки по три в ряд с цветными статусами и сводкой, canvas — рёбра графа сделаны заметнее.

**Найденный при переделке баг: умершие процессы не исчезали из истории.** `Series::last_value()` возвращает последнее *измеренное* значение, пропуская разрывы, поэтому завершившийся процесс навсегда оставался в топе по CPU со своим старым числом — а имя у него уже не находилось, и строка выглядела как «PID, пустое имя, 6,2 %». Теперь ряды завершившихся процессов удаляются из истории, а топ строится по текущему снимку и только по процессам с измеренным CPU. Добавлен `Series::latest_value()` — «известно раньше» больше не подменяет «неизвестно сейчас».

**Крейт `mcpad-gui` разделён на lib и bin:** вся логика окна живёт в `lib.rs`, бинарь только разбирает аргументы. Так логику видно тестам, а не только в рантайме.

**Проверено:** 179 тестов, clippy с `-D warnings` и `cargo fmt --check` — чисто; окно снято снимками во всех пяти разделах, в тёмной и светлой темах, в русской и английской версиях, с выбранным процессом (панель сведений) и без него.

В трейт пробы добавлены `terminate_process` и `set_priority`, в перечень возможностей — `process_control` и `process_priority`; они сразу видны в разделе «Возможности».

**Баги, найденные при сверке.** Шесть из них — настоящие, а не опечатки в тестах.

1. **Текст фильтра терялся.** Строка поиска вынималась из состояния через `std::mem::take` до отрисовки центральной панели, и список фильтровался по пустой строке: поиск не находил ничего. Теперь фильтр передаётся в отрисовку параметром.
2. **Кириллица не переводилась в нижний регистр.** `to_ascii_lowercase` трогает только ASCII, поэтому `ИМЯ:rust` и «Обычный» не распознавались — имя поля и класс приоритета не подходили. Поймал тест; заменено на `to_lowercase`.
3. **JSON-экспорт отдавал числа строками** (`"pid": "1"` вместо `"pid": 1`). Файл должен брать машина, а не человек: числа остаются числами, неизвестные значения — `null`.
4. **Карта родителей строилась из отфильтрованных строк.** При текстовом фильтре «скрыть системные» переставал видеть системное дерево, а группа называлась «pid N». Теперь карта берётся из снимка целиком: родитель, отфильтрованный из списка, всё равно известен.
5. **Смена приоритета не собиралась на Linux и macOS.** У `setpriority` второй аргумент — `id_t`, а он беззнаковый (`u32`), тогда как `kill` принимает `pid_t` (`i32`). Windows собирался, а Linux и macOS падали — это увидел CI, а не локальная сборка. Теперь типы выверены по исходникам `libc`, и код проверяется локально через `cargo check --target x86_64-unknown-linux-gnu` и `--target aarch64-apple-darwin`: линкер для проверки типов не нужен.
6. **Тест мог послать сигнал всем процессам.** На Linux `kill(-1, SIGTERM)` бьёт по всем процессам пользователя, а `kill(0, …)` — по всей группе. Тест брал «заведомо несуществующий» PID `u32::MAX`, который в `pid_t` превращается в `-1`: на Windows это было безобидно, а на Linux — уронило CI. Теперь PID проверяется до сигнала: ноль и значения вне диапазона отклоняются с ошибкой, а тесты берут `i32::MAX` (заведомо выше любого реального PID).
7. *(Из волны 6)* умершие процессы не исчезали из истории: `Series::last_value()` возвращал последнее *измеренное* значение, пропуская разрывы.

**Честный остаток.** Перечисленное выше «нет» — не забытость, а вещи, которым нужны источники данных или отдельные крейты, и которые одной волной не закрываются.

- Вкладки свойств кроме модулей, поиск по дескрипторам, дампы, приостановка и affinity — нужен новый источник данных (дескрипторы, потоки, карта памяти, привилегии), а не только интерфейс.
- Службы, сеть, диск, GPU, датчики — новые источники данных и отдельные крейты плана (`mcpad-inspect`, `mcpad-gpu`).
- Трей, мастер первого запуска, политики и лимиты, история и тренды, MCP-сервер, AI-ассистент, плагины — это `mcpad-mcp`, `mcpad-ai`, `mcpad-history`, `mcpad-policy`, `mcpad-tui` по §9 и §11 плана.
- Текущий класс приоритета процесса не показывается: чтобы его честно показать, его надо собирать в снимке, а на Windows это стоит открытия каждого процесса. Сейчас приоритет можно менять, но не читать.
- Мультисортировка по нескольким колонкам в исходниках тоже не встречается: в Task Explorer и System Informер сортировка одна колонка с тремя состояниями.

**Проверено:** 212 тестов, clippy с `-D warnings` и `cargo fmt --check` — чисто; окно снято снимками: список процессов с выбранным процессом и панелью действий, группировка по приложению с итогами в заголовках группы, быстрые фильтры и скрытие системных, режимы поиска, раздел «Возможности» с новыми возможностями `process_control` и `process_priority`.

**Релиз перевыпускался трижды — и это оказалось правильно.** Первая попытка упала на Linux и macOS: у `setpriority` второй аргумент — беззнаковый `id_t`, а не `pid_t`. Вторая — из-за теста, который брал «несуществующий» PID `u32::MAX`, а в `pid_t` это `-1`, то есть сигнал **всем** процессам пользователя; на Windows это было безобидно, на Linux уронило CI. Обе ошибки нашлись по логам CI, а не локальной сборкой, потому что код этих платформ на Windows не собирается. Правило на будущее: **код чужих ОС проверяется на их целях до отправки в CI**, иначе первый же прогон CI становится тестом на живой машине.
